## Wordstat: найдена и исправлена причина пустых частотностей + полный список фраз (24 августа)
Владелица прогнала M7 живьём (первый реальный платный прогон с Wordstat) —
результат: частотность и сезонность в SEO-02 везде «не замерено», хотя API
рабочий (см. выше). По логам Vercel (`get_runtime_logs`) нашла 2 запроса
`/api/wordstat` со статусом 400 в момент прогона — `gatherWordstatData`
вызывался, но Yandex отклонял оба сформированных запроса.

**Причина (подтверждено живым тестом владелицы через консоль браузера):**
Wordstat матчит по точной строке, а не по смыслу (в отличие от Tavily-поиска,
где длинная фраза — нормально). Прежний код клеил длинный якорь
`продукт+ниша+рынок` — «попап для интернет-магазина» → `totalCount: 2`,
пусто. Короткое ядро — «попап для сайта» → `totalCount: 157`,
10 associations. Длинная склейка почти всегда возвращает пустоту, отсюда
сплошное «не замерено» даже при полностью рабочем и настроенном API.

**Исправлено (`624e49f`, `85d9a2f`, `7c24f08`):**
1. `api/wordstat.js` — при ошибке от Yandex теперь `console.error` с
   phrase+статусом+телом ответа (раньше причина ошибки просто отбрасывалась,
   в логах было не видно, ПОЧЕМУ 400).
2. `gatherWordstatData` — якорь теперь короткое ядро продукта (до « для »/
   « for »), ниша/рынок добавляются ВТОРЫМ, более широким якорем, а не
   единственным способом искать. `numPhrases` поднят с 30 до 50.
3. Отдельная просьба владелицы, зафиксирована в коде: она вручную заходит в
   Wordstat и смотрит ПОЛНЫЙ список похожих запросов по теме — хочет то же
   самое автоматически, без отбора/додумывания моделью (раньше модель видела
   Wordstat-данные только как контекст для SEO-02 и сама решала, что взять —
   могла показать не всё). Теперь после ответа модели КОДОМ (не LLM)
   приклеивается отдельный блок «Полный список запросов по Wordstat» — все
   найденные фразы+частотности как вернула сама Wordstat, без нулевых
   показов, отсортированные по частотности. Модель этот блок не пишет и не
   видит — гарантированно без урезания и без выдумок.

**НЕ ПРОВЕРЕНО живым прогоном** (у владелицы сейчас нет бюджета на
Tavily/OpenAI/Wordstat — прогон отложен, не забыть вернуться):
- [ ] ↺ на M7 у любой уже исследованной ниши → в SEO-02 должна появиться
  реальная частотность с пометкой «Wordstat» вместо повсеместного
  «не замерено» (главная проверка — воспроизводится ли ещё пустой результат
  с новыми короткими якорями, или проблема решена).
- [ ] В конце результата M7 должен появиться новый блок «Полный список

- [ ] Если частотность в SEO-02 всё ещё пустая, а новый блок непустой —
  значит проблема не в Wordstat, а в том, что модель не матчит кластеры

```sql
-- Колонка владельца + RLS на projects
-- ВАЖНО: сначала БЕЗ not null — иначе ALTER падает на существующих строках
-- ("column owner_id contains null values"), потому что auth.uid() в default
-- работает только в контексте запроса от приложения, а не в SQL Editor'е
-- (там во время самого ALTER это значение пустое). Сначала добавляем колонку,
-- затем backfill вручную (см. миграцию ниже), и ТОЛЬКО ПОТОМ включаем not null.
alter table projects add column if not exists owner_id uuid default auth.uid() references auth.users(id);

-- Миграция существующих строк на первый (её) аккаунт — ДО not null
update projects set owner_id = '<ЕЁ_USER_ID>' where owner_id is null;

-- Теперь можно требовать not null — пустых строк уже нет
alter table projects alter column owner_id set not null;

alter table projects enable row level security;
create policy "own projects" on projects
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());

-- publications/metrics_snapshots — изоляция через project_id -> projects.owner_id
alter table publications enable row level security;
create policy "own publications" on publications
  for all using (project_id in (select id from projects where owner_id = auth.uid()))
  with check (project_id in (select id from projects where owner_id = auth.uid()));

alter table metrics_snapshots enable row level security;
create policy "own metrics" on metrics_snapshots
  for all using (publication_id in (
    select p.id from publications p join projects pr on pr.id = p.project_id
    where pr.owner_id = auth.uid()))
  with check (publication_id in (
    select p.id from publications p join projects pr on pr.id = p.project_id
    where pr.owner_id = auth.uid()));

-- trend_snapshots — та же связь через project_id
alter table trend_snapshots enable row level security;
create policy "own trends" on trend_snapshots
  for all using (project_id in (select id from projects where owner_id = auth.uid()))
  with check (project_id in (select id from projects where owner_id = auth.uid()));

-- domain_registry — ОБЩИЙ реестр (не приватные данные), доступ любому вошедшему
alter table domain_registry add column if not exists refreshed_at timestamptz not null default now();
alter table domain_registry enable row level security;
create policy "any authenticated user" on domain_registry
  for all using (auth.role() = 'authenticated') with check (auth.role() = 'authenticated');
```

## M7: второй регрессионный баг в тот же день — якоря Wordstat (`4b3b2b4`)

Владелица разобрала полный отчёт и поймала ещё один реальный баг (не в VoC —
в частотности M7): SEO-02 полностью «не замерено», а сырой список Wordstat
внизу отчёта — про магазин инструментов (vseinstrumenti.ru), хотя продукт —
попапы для лидогенерации.

Причина: вчерашняя эвристика «обрезать niche до первого „для“»
(`core = product.split(/для/)[0]`) сломалась на реальном брифе — niche была
«инструмент для захвата лидов/умные попапы с ИИ», обрезка дала «инструмент»
(случайное слово). Regex не может надёжно отличить хвост-уточнение («попап
ДЛЯ сайта» — резать можно) от «для» как части смысла niche («инструмент ДЛЯ
захвата лидов») на свободном тексте.

Модель, кстати, повела себя правильно — увидела, что блок реальных чисел
не пересекается по смыслу с её кластерами, и честно написала «не замерено»
вместо того, чтобы притянуть чужие цифры. Анти-галлюцинационная защита
сработала как задумано на мусорном входе — сам вход был проблемой.

**Фикс:** `extractWordstatSeeds` — маленький отдельный вызов модели вместо
regex, просит 2-3 короткие поисковые фразы под ТИП продукта (не под
описание пользы). При сбое — старая эвристика как запасной вариант.
Плюс `relevantKeywordFilter` — держит только фразы, делящие значимое слово
со словарём темы (сиды+niche+format+services), сравнение по стемму (первые
5 букв, не точное совпадение — иначе «попап» не совпал бы с «попапы» из-за
русских окончаний). Второй пункт — владелица явно попросила отсекать
нерелевантные ассоциации даже при хорошем якоре.

**Wordstat-якоря — проверено живьём 26.08, найдена и починена вторая грань
той же проблемы** (`78463af`): вчерашний фикс сработал частично — якорь
«попап» дал реальные данные (6456/мес), SEO-02 больше не пустой. Но
владелица заметила: (1) кластеры про «умные попапы»/«AI попап» всё равно
«не замерено» — общий якорь «попап» не подсказывает Wordstat AI-специфичные
варианты; (2) «попап» — омоним (ещё и рыболовный термин, насадка для карпа),
в сыром списке попал мусор («попапы для рыбалки», «карп попап»). Промпт
`extractWordstatSeeds` дополнен двумя правилами: якорь отдельно под то, что
ОТЛИЧАЕТ продукт (не только категория), и проверка однословных якорей на
риск омонимии. Потолок якорей 3→4.

**Проверено 26.08 — прогресс, но поймана третья грань (`27d5e52`):**
предыдущий фикс сработал частично — 5 из 8 кластеров получили реальные
числа, включая AI-специфичные («ии виджет для сайта» = 10). Но новый якорь
«захват лидов» вскрыл слабость самого фильтра релевантности: Wordstat
вернул «захватывающие фильмы» (99625, максимум в списке) — общий корень
«захват» (изъять) совпал с «захватывающий» (увлекательный), фильтр это
пропустил, потому что сравнивал по ЛЮБОМУ одному общему слову с общим
мешком слов всего брифа. Переписан: сравнение с КАЖДЫМ сидом отдельно,
фраза проходит только если содержит ВСЕ значимые корни целиком хотя бы
одного сида — «захватывающие фильмы» больше не пройдёт (нет корня «лид»).

Однословные сиды («попап») по-прежнему уязвимы к омонимии — это
принципиально не чинится фильтром, только выбором сида (уже в промпте
extractWordstatSeeds).

**Закономерность за три захода:** каждый живой прогон M7 вскрывал НОВУЮ
грань одной и той же проблемы (regex → общий якорь → слабый фильтр) — не
потому что чиню плохо, а потому что синтетических тестов для этой части
нет и не может быть (реальные слова русского языка непредсказуемы). Стоит
считать это ожидаемым по одному фиксу на прогон, не багом процесса.

**Проверено 26.08 — строгий фильтр оказался перелечиванием, откачена
(`ca817ae`):** следующий прогон вернулся к 1/8 кластеров с данными вместо
5/8. Разбор: строгий фильтр («все корни сида») тем же приёмом, что исправил
«захватывающие фильмы», снёс и «AI попап» под сид «умный попап» — с точки
зрения подсчёта слов это ОДНА И ТА ЖЕ ситуация (1 совпадение из 2 слов),
отличить «то же самое другими словами» от «случайный корень, другой смысл»
без понимания смысла невозможно. Перепроверила предыдущий прогон: модель
сама, когда пишет SEO-02, ни разу не перепутала «захватывающие фильмы» с
реальными кластерами — проблема была только в сыром списке-приложении
(косметика), не в фактической точности SEO-02. Вернула мягкий фильтр
(«хотя бы одно общее слово») — смысловую точность оставляем модели, у неё
она реально есть, лексика её только имитирует и ломает по пути.

**Итог трёх заходов за два дня:** regex-обрезка → короткие сиды через
модель + правила про омонимы → фильтр релевантности мягкий → строгий →
снова мягкий (текущее состояние). Каждый живой прогон открывал новую грань
одной задачи — считать это нормальной ценой работы с живым языком, не
процессным сбоем.

**НЕ ПРОВЕРЕНО живьём**: откат мягкого фильтра ещё не видели в деле —

## M7 упал с «Failed to fetch» — обрыв сети, не баг паузы (27.08, `f92d046`)

Первый прогон с новой паузой: фразы предложились нормально, владелица их

**Диагноз по логам Vercel (не по догадке):** ВСЕ вызовы вернули 200 — 5×
`/api/search`, 5× `/api/wordstat`, `/api/proxy` (сама модель), `/api/projects`
(сохранение). Сервер отработал полностью; ответ модели не дошёл до браузера —

запросы идут по относительным путям, то есть same-origin, там CORS-заголовки
вообще не проверяются. Таймаут функции исключён: между вызовом модели и
сохранением 15 секунд, до любого лимита далеко.

**Что чинилось (следствие, не причина):** `callGPT` — единственный вызов без
обработки сбоя, поэтому именно он ронял весь модуль; `callSearch`/
`callWordstat` молча возвращают `[]`/`null` и живут дальше. Одна сетевая
икота стоила целого прогона вместе с уже оплаченными поисками и Wordstat.
Теперь `authFetch` делает 3 попытки с паузой ТОЛЬКО на сетевой обрыв (fetch
бросает исключение); HTTP-статусы 4xx/5xx возвращаются как есть — их
ретраить нельзя, их разбирает вызывающий код. Помогает всем вызовам сразу.

**Два бага вчерашней паузы, найденных при этом же разборе:**
1. `continueAfterSeeds` терял параметры прерванного прогона — `rerunNiche`
   (в пересчёт могли уйти соседние ниши) и `regenNote` (замечание «что
   поправить» молча пропадало). Теперь они сохраняются в `pausedRunRef`.
   `forceRerun` намеренно НЕ переносится: он выкидывает всю запрошенную
   цепочку, а к моменту паузы M2…M6 уже посчитаны и оплачены — повтор стёр

## M7: терялась частотность самих подтверждённых фраз (28.08, `e14a764`)

Жалоба владелицы: «в таблицу попадают другие ключи, чем мы пишем, и мало —
а должны быть самые главные ключи по нише».

**Разбор прогона:** пауза с подтверждением фраз отработала правильно, и
модель тоже — она взяла подтверждённые фразы как кластеры SEO-02 («попап для
интернет-магазина», «умный попап для сайта»…). Но частотности не было ни у
одной: во всей таблице «не замерено», кроме единственной случайной
ассоциации «попап что это для сайта | 140». В сыром блоке «Полный список» —
тоже ровно одна фраза.

**Причина — в моём коде, не в подборе фраз.** Wordstat на каждый запрос
возвращает `totalCount` — частотность именно введённой фразы.
`fetchKeywordFrequencyData` её запрашивала и молча выбрасывала: в
`frequencies` попадали только `results`/`associations`, то есть похожие
фразы, предложенные самим Wordstat. Выходило ровно наоборот задуманному —
ключи, отобранные человеком вручную, были ЕДИНСТВЕННЫМИ без замера, а в
отчёт шли случайные ассоциации. Пауза с подтверждением фраз (26.08) при
этом работала правильно — просто её результат дальше терялся.

**Исправлено:** каждая подтверждённая фраза идёт в `frequencies` со своим
`totalCount` и флагом `confirmed`; `relevantKeywordFilter` их не выкидывает
никогда (сверка и по флагу, и по списку сидов — у Google Ads `totalCount`
нет); потолок сидов 4 → 12 (список отобран человеком, обрезать его до первых
четырёх — терять ровно ту работу, ради которой делалась пауза: владелица
дополняла список, а фразы с 5-й не запрашивались вообще); `buildM7Prompt`
помечает их «ОПОРНАЯ ФРАЗА (выбрана владелицей)» и требует отдельный кластер
на каждую.

**Известное ограничение (осознанно):** мягкий лексический фильтр по-прежнему
пропускает омонимы («попапы для рыбалки» делит корень с «попап»). Это шум в
сыром списке, но больше не подмена главных ключей — опорные фразы теперь
гарантированно в таблице со своими числами.

**НЕ ПРОВЕРЕНО живьём** — ждёт следующего прогона M7.

## M7: лексический фильтр убран — он был причиной «мало ключей» (29.08, `1c4484d`)

Жалоба владелицы по прогону 28.08: мало ключей в таблице (нужны сотни на
выбор, «как было в старых отчётах»), в таблице кластеры с почти нулевой
частотностью, на графике виден один столбик, и «обратка» — вообще не ключ.

**Замер по факту:** в сыром блоке «Полный список» — 8 фраз. Во главе
«обратка» 202427/мес. В таблице кластеры с 11 и 37 показов. В chartData 9
кластеров, из них 3 с `volume: null` и один выброс 202427 — остальные на
его фоне неразличимы.

**Одна причина у всех симптомов — `relevantKeywordFilter`.** Он требовал
общий корень с сидом и делал ровно обратное задуманному:
- выкидывал ХОРОШЕЕ: Wordstat отдаёт близкие ПО СМЫСЛУ фразы
  («всплывающее окно» к сиду «попап») — общего корня нет, фраза терялась.
  Отсюда 8 строк вместо сотен;
- оставлял МУСОР: «обратка», «туда обратно как пишется» делят корень
  «обрат» с сидом «форма обратного звонка» — проходили.

Фильтр задумывался как защита от плохих АВТОМАТИЧЕСКИ подобранных сидов, но
с 26.08 сиды подтверждает человек — защита переехала выше по потоку, а
фильтр остался вредить. Четыре захода на его логику (25-29.08) показали:
отличить «то же самое другими словами» от «случайный общий корень» подсчётом
слов нельзя, нужен смысл.

**Решение — разделить роли:**
- сырой список отдаётся ПОЛНОСТЬЮ (фильтр и `significantStems`/`wordStem`
  удалены) — как при ручной работе в Wordstat, владелица выбирает сама;
- отсев по смыслу для ИТОГОВОЙ таблицы делает модель, которая смысл
  понимает: в `buildM7Prompt` добавлен блок правил отбора кластеров
  (отбрасывать омонимы и чужие темы с примерами реального мусора,
  сортировать по частотности, не заполнять таблицу почти нулевыми,
  давать 12-25 кластеров вместо 5-8);
- сезонность считается в первую очередь для опорных фраз владелицы;
- график: только измеренные кластеры, по убыванию, максимум 15 (раньше
  «не замерено» рисовалось нулевым столбиком — читается как «спроса нет»,
  хотя значит «не измеряли»).

**НЕ ПРОВЕРЕНО живьём** — ждёт следующего прогона M7. Ожидаемо: сотни фраз
в сыром списке, 12-25 кластеров в таблице, читаемый график.

## M7: только замеренные кластеры + группы ВЧ/СЧ/НЧ (29.08, `c2700ed`)

Вопрос владелицы: «почему в таблицу попадают ключи, в которых не определены

Возражений нет — она права, и это была недоработка правил, а не сбой.

**Причина:** промпт разрешал брать кластеры и из evidence (веб-поиск), где
числа нет по определению, требуя лишь честно пометить «не замерено». В итоге
половина SEO-02 состояла из строк, бесполезных для SEO-работы: по ним нельзя

**Исправлено:**

  вручную» под таблицей. Единственное исключение: замер недоступен целиком
  (не настроен/не сработал) — тогда прежнее поведение с явной пометкой,
  иначе модуль не выдал бы ничего.
- Новая колонка «Группа (ВЧ/СЧ/НЧ)». Границы модель определяет по
  фактическому распределению чисел В ЭТОЙ нише, не по универсальным порогам

  одному кластеру на статью.
- `numPhrases` 50 → 200 (потолок API 2000). Отобрать 30 кластеров можно
  только из сотен фраз. Цена не меняется: это один вызов на фразу независимо
  от numPhrases, просто просим больше строк за раз.
- CHART DATA: `volume` теперь всегда число, добавлено поле `group`.

## M7: правая колонка Wordstat — источник мусора (29.08, `25b4136`)

Прогон 28.08 дал в списке ключей «портал» (3 281 965), «скачать мод на
трансформеров», «как выглядит кляп», «ry7 ru интернет магазин», «адаптация
персонала это». Владелица: «опять какая-то чушь».

**Причина найдена и она структурная, не косметическая.** Wordstat отдаёт две
разные вещи, а я сваливала их в один список:
- `results` — ЛЕВАЯ колонка, фразы, СОДЕРЖАЩИЕ запрос. По определению на тему.
- `associations` — ПРАВАЯ колонка, «похожие запросы». Связь ПОВЕДЕНЧЕСКАЯ
  («что ещё искали эти люди»), а не по словам запроса. Именно отсюда и
  «портал», и «кляп» — ни одного общего слова с подтверждёнными фразами.

Профессиональная практика сбора семантики (проверено по источникам, PR-CY /
eLama): правая колонка — подсказка для НОВЫХ идей, а не готовое ядро, её
запросы «часто неподходящие для прямого использования». То есть это была моя
ошибка проектирования, а не сбой инструмента.

**Сделано:**
- в ядро идёт только левая колонка + сама подтверждённая фраза (`totalCount`);
- ассоциации не выбрасываются, а уходят в ОТДЕЛЬНЫЙ раздел отчёта «Похожие
  запросы — идеи для расширения, НЕ ядро», с оговоркой, откуда там
  постороннее. Годное оттуда владелица может вручную добавить в список фраз
  на следующем прогоне — это и есть их настоящее назначение;
- добавлены минус-слова `NOISE_PATTERNS` (торренты, читы, вакансии,
  правописание) — стандартный приём сборщиков.

**Важно про природу фильтра, чтобы не повторить прошлые ошибки:** минус-слова
это ЧЁРНЫЙ список — убрать заведомо чужие темы. Все мои прошлые неудачные
фильтры (25-28.08) были БЕЛЫМИ — «оставить только похожее на сид» — и потому
резали хорошее («всплывающее окно» не содержит слова «попап»). Чёрный список
так не умеет: он трогает только то, что в нём перечислено. В список
сознательно НЕ включены «скачать», «бесплатно», «отзывы» — в разных нишах это
законные коммерческие запросы (проверено на «скачать попап для сайта»).

**НЕ ПРОВЕРЕНО живьём** — ждёт прогона M7.

**Чего мы по-прежнему НЕ делаем в сравнении с профи-сборщиками** (key.so,
Rush Analytics, Key Collector) — честный список пробелов:
1. **Кластеризация по выдаче** — профстандарт: две фразы в один кластер, если
   по ним пересекаются URL в топ-10. У нас кластеры лепит модель по смыслу.
   Требует SERP-данных по каждой фразе — отдельный платный источник.
2. **Поисковые подсказки** (Яндекс/Google Suggest) как второй источник сбора —
   дёшево и даёт живые формулировки, которых нет в Wordstat.
3. **Ключи конкурентов** — «по каким запросам ранжируется конкурент». Это
   основа key.so; требует своей базы выдачи, сами не соберём.
4. **Частотности в кавычках и с восклицательным знаком** («!фраза») —
   отсеивают накрутку и словоформы; Wordstat API операторы не поддерживает
   (проверено 22.08), поэтому наши числа — широкое соответствие, их нельзя
   читать как точный трафик.

## Google Ads: забрано то, что уже приходило в ответе (29.08, `2da9f62`)

Вопрос владелицы «а что из этого есть в Google?» (о пробелах против key.so)
привёл к находке: три полезные вещи Google отдавал, а мы их не читали.

**Что было доступно и не использовалось:**
1. `monthlySearchVolumes` — помесячная история за 12 месяцев В ТОМ ЖЕ ответе
   GenerateKeywordIdeas. Мы писали «сезонность не замерено» для всех
   нероссийских рынков, хотя данные уже лежали в ответе. (У Яндекса для
   этого нужен отдельный вызов `dynamics` — там наше поведение было верным.)
   Нюанс: месяц у Google приходит названием (`JANUARY`), не числом —
   приводим к `YYYY-MM`, формату Wordstat, чтобы дальше по коду был один вид.
2. `competition` (LOW/MEDIUM/HIGH) + `competitionIndex` (0-100) по каждому
   ключу. Колонку «Конкуренция» в SEO-02 до сих пор заполняла прикидка
   модели; теперь измеренная величина идёт в промпт, и модель обязана брать
   её как есть, а свою оценку давать только где числа нет.
3. `urlSeed`/`keywordAndUrlSeed` — URL как затравка вместо фразы, то есть
   «по каким запросам работает вот этот сайт». У Wordstat такого нет
   в принципе; это то, ради чего покупают key.so. Домены берутся из уже

**Нюанс реализации:** опорная фраза у Google узнаётся иначе, чем у Яндекса —
`totalCount` там нет, поэтому `confirmed` ставится результату, совпавшему с
самим сидом.

**НЕ ПРОВЕРЕНО и проверить пока нечем:** Basic Access у Google не одобрен,
заявка в комплаенсе (первая отклонена — в форме был указан профиль LinkedIn
вместо сайта; ответ с подробным описанием бизнес-модели и скриншотами
отправлен 29.08). До их решения весь Google-путь непроверяем.

**Что Google НЕ закрывает** (остаётся пробелом против профи-сборщиков):
кластеризация по пересечению выдачи — Ads API данных выдачи не даёт, а
Custom Search JSON API закрыт для новых клиентов. Поисковые подсказки
(Suggest) есть, но эндпоинт неофициальный — одинаково хрупко и у Google, и
у Яндекса.

## Переезд на платформу: решения и первый шаг (29.08, `8646bd7`, `29639b3`)

**Кто делает оболочку — изменилось.** В первом плане контент-машины было
«контент-машина въезжает первой», но их агент сам это пересмотрел и передал
оболочку нам, аргумент верный: у нас JS, 17 React-компонентов и уже рабочая
авторизация на Supabase JWT — то есть ядро оболочки написано и проверено
живьём. У них Python-ядро без интерфейса. Стек — Next.js.

**Их поправка, с которой согласилась:** «оболочку делает один» не спасает от
несовместимости модулей. Спасает договорённость о том, КАК модуль
подключается, до кода: маршруты, объявление в навигации, кто вошёл и какой
клиент активен, подключён ли модуль этому клиенту, где живёт состояние
проекта и где — состояние модуля. Они пишут черновик со своей стороны, я — со
своей; сводим в один документ и только потом код оболочки. Это единственная
часть, которую нельзя делать параллельно.

**Первый шаг выноса сделан.** Порядок предложили они и он правильный:
контракт первым, потому что это общая точка отказа. `lib/contract.js` —
13 чистых функций (`buildAgentPackage`, `buildModuleEntry`, `parseMdTables`,
`pickTable`, `pickColumn`, `withStableIds`, `splitMdRow`, `isMdSeparator`,
`isPerNiche`, `dropOrphans`, `nichesOf`, `resKey`, `GLOBAL_MODS`), ни React,
ни DOM, ни JSX. `index.html`: 4932 → 4745 строк.

Убрана единственная грязная зависимость: `buildModuleEntry` лез прямо в
`MODULES` — конфиг ИНТЕРФЕЙСА, из-за чего сборщик контракта нельзя было ни
вынести, ни проверить отдельно. Теперь принимает `titleOf`, а `index.html`
передаёт функцию поиска. Остальные места вызова не менялись: имена
разбираются из `CAContract` в начале Babel-скрипта. Сборка по-прежнему не
нужна; при переезде обёртка IIFE меняется на `export`.

**`tests/contract.test.js` — 17 проверок, БЕСПЛАТНО и без установок**, на
встроенном в macOS движке JS: `osascript -l JavaScript tests/contract.test.js`.
Проверяет в том числе то, ради чего поднимали `schema_version` до 3 (ниши не
смешиваются), плюс `failed_modules`, `status`, отброс «сирот». Все проходят.
Раньше убедиться, что контракт цел, можно было только платным прогоном.

**Дальше по их порядку:** разбор таблиц (частично уехал вместе с контрактом),
потом промпты. Оркестратор `run()` — последним и с полным разбором каждого
куска: в нём накопились вещи, найденные только живыми прогонами (пауза перед
M7, остановка цепочки при падении модуля, ретраи, логика по нишам).

**Правило до переезда:** правки в промптах, логике отбора и контракте — делаю
свободно, они переезжают без переделки. Новые экраны в `index.html` — только
если без них нельзя работать сегодня.

## Нумерация модулей: подписи меняем, идентификаторы — нет (10.09)

Владелица спросила, можно ли переименовать модули. Ответ по фактам: **подписи
да, идентификаторы нет.**

В структуре модуля `label` уже отделён от `id` (например `id:'M1'`,
`label:'M1.1'`), так что человеко-читаемые названия правятся свободно.

**`id` трогать нельзя**: он лежит в коде (`requires`, `offChain`), в контракте
и **в сохранённых проектах** — результаты в базе хранятся с ключом по `id`.
Переименование без переноса ломает старые исследования клиентов.

**Отложено с условием** (в памяти — `todo-rename-module-ids`): переименовывать
только после того, как все правки доведены и проверены живым прогоном, и
только **написав перенос заранее** — карту «старый id → новый id» и проход по
сохранённым результатам.

Целевой порядок, если дойдём: номер = место в цепочке, то есть контент-радар
станет M3, голос клиента M4, персоны M5, офферы M6.

## Открытый вопрос владелице: кому достаётся бесплатный порог (11.09)

Всплыло при сверке сметы с контент-агентом. Подтверждено по коду, не догадка:
`api/wordstat.js` подставляет один `YANDEX_FOLDER_ID` в каждый запрос,
`api/google-ads.js` — один `CUSTOMER_ID` и один `REFRESH_TOKEN`. Клиентских
ключей в архитектуре нет и не предусмотрено.

Следствие: любой порог поставщика — бесплатная квота, лимит — ОБЩИЙ на всех
клиентов сразу и тратится в порядке живой очереди. Клиент, запустивший
исследование первого числа, съедает бесплатное у того, кто запустит двадцатого.
Это свойство архитектуры, от тарифа не зависит.

Решать владелице, варианты:
1. делить порог по клиентам (квота на каждого);
2. не делить, считать по среднему и заложить в цену;
3. заложить в себестоимость и клиенту вообще не показывать;
4. не делить, но показывать ФАКТИЧЕСКИЙ расход после прогона вместо оценки до —
   с `keywordCallCount` это теперь возможно.

Отдельно: точную цену ДО запуска показать нельзя в принципе, если тариф
пороговый — она зависит от того, сколько уже израсходовано в этом месяце.
Остаток порога облако не сообщает; посчитать его самим можно (сумма
`keywordCalls` за месяц), но это будет наша оценка, а не факт поставщика, и
разойдётся при любом обращении мимо нашего кода.

Ждёт: тариф владелицы у Яндекс-облака.

## Сайт и выгрузка рисуют одним кодом (11.09)

приложения. Ограничитель отдельно чинился: первое правило внутри каждого
`@media` оставалось свободным, потому что перед ним стоит `{`, а не `}`.

## Главный урок дня: брать готовое, а не переписывать

Три раза подряд я читала утверждённый код и писала «то же самое» своими
словами. Каждый перевод терял деталь: цвета вердиктов (в макете в :root
осталась палитра «Тиффани», где «не идём» ЖЁЛТЫЙ — в живом макете её перебивает
скрипт, в выгрузке перебивать некому), блок «как читать фигуру», имена классов
(`ncard2`, а не выдуманный `ncard`).

Теперь код блоков вставлен ДОСЛОВНО, подменены только данные и id контейнеров.
И подгонять надо данные под утверждённый код, а не наоборот: кольцо ждёт массив
`[ID, сегмент, кто это, потребность, платёжеспособность, уверенность, доля]` —
значит рендерер отдаёт ровно такой массив.

**И вторая причина промахов:** в разборах и библиотеке по 2–3 блока `<style>`,
а все мои проверки читали только первый. Отсюда «пропавший» CSS, классы без
стилей и повторные попытки собрать то, что уже было готово.

## ПРАВИЛА, КОТОРЫЕ СТОИЛИ ЦЕЛОГО ДНЯ — не нарушать

1. **Брать готовое дословно, а не переписывать «по смыслу».** Каждый мой
   перевод утверждённого кода своими словами терял деталь: цвета вердиктов,
   блок «как читать фигуру», имена классов (`ncard2`, а не `ncard`).
   Подгонять надо ДАННЫЕ под утверждённый код, а не код под данные.
2. **Вырезать функции по надёжной границе (`\n})();`), а не счётом скобок.**
   Внутри кода есть фигурные скобки в строках; счёт обрезает функцию на
   середине, и тогда НЕ РАЗБИРАЕТСЯ ВЕСЬ скрипт — пустыми становятся все блоки
   сразу. Ловится `tests/report-js.test.js`, гонять после каждой правки BLOCK_JS.
3. **Каждый блок рисуется в своём try.** Был один общий — падение одного блока
   уносило все следующие.
4. **Переменные палитры задавать в отчёте ЯВНО.** В макете `--mid`, `--back`,
   `--front`, `--acc-ink`, `--acc-strong/mid/quiet` проставляет скрипт
   переключения тем; в выгруженном файле его нет, и остаются значения «Тиффани»

откроет, и у нового сайта её нет вовсе. Отсюда я сделала вывод «интеграцию не
делать», и вывод был неправильный.

**Верная постановка:** исследование должно давать демографию НИШИ — то, чего у
клиента нет и быть не может, особенно на новом сайте. Её и берут из рекламного
кабинета, но **нашего**: площадки умеют оценивать охват по полу, возрасту и
интересам. Это рыночная величина, к конкретному сайту отношения не имеющая,
и для неё достаточно любого аккаунта — в том числе аккаунта владелицы.

Где искать, по убыванию уверенности:
- **ВК Реклама** — оценка охвата по возрасту, полу, интересам; по России самая
  полная база. Первый кандидат.
- **Яндекс Аудитории** — сегменты по интересам с оценкой размера.
- **Google Ads** — планировщик охвата; демография слабее, по России почти
  бесполезна.
- Плюс отраслевые исследования из поиска со ссылкой [n] — это промпт уже умеет.

**НЕ нужно:** доступ к Метрике клиента, OAuth за каждого клиента, хранение их
токенов. Всё это отпало вместе с неверной постановкой.

**Первый шаг — проверка, а не код:** какие из площадок отдают оценку охвата
ЧЕРЕЗ API, а какие только в интерфейсе руками. Это разница между «встроим в
прогон» и «владелица смотрит сама и вписывает в бриф». Проверять по
документации: я уже дважды судила по общему устройству и один раз ошиблась.

**Вторая трудность, о ней сразу:** оценка охвата даётся по ИНТЕРЕСАМ, а не по
поисковым запросам. Связь «ниша → набор интересов для таргетинга» придётся
задавать явно, иначе получим красивое число не о том.
