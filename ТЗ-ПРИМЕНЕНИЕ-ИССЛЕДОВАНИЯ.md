# ТЗ: применение исследования — генерация готового контента

**Создано:** 2026-08-16 · **Статус:** к разработке
**Контекст:** часть проекта [[личный бренд / CA Research]] (`~/Projects/personal-brand/`), Спринт 2.

## Проблема

Само по себе исследование ЦА (M1-M7) как отчёт — недостаточная ценность для платящего клиента. Гипотеза, зафиксированная владелицей 16.08.2026: **нужно применение**, то есть готовый к публикации контент, сгенерированный на основе исследования, а не отчёт, который клиент должен сам интерпретировать и превращать в текст.

## Референс-конкурент

Сервис **Никиты Корытина**: делает ЦА-исследование по промптам → генерирует пост на основе его личного копирайтерского опыта. Известный факт (со слов клиента владелицы, заказчика LeadYup): статья, сгенерированная этим сервисом и опубликованная на VC, принесла клиенту 1-2 лида. Значит, спрос на механику «исследование → готовый текст» подтверждён практикой, не только гипотеза.

**Гипотеза differentiator'а:** промпты исследования CA Research (M1-M7, с реальными данными Wordstat и evidence+[n] из Tavily) глубже, чем у сервиса Корытина. Но глубина исследования сама по себе не гарантирует качество сгенерированного контента — её ещё нужно правильно транслировать в текст, не потеряв при сжатии в формат.

## Задача

Построить генерацию готовых форматов контента поверх результатов исследования M1-M7 (и, где релевантно, M8 трендов):

1. **Статья** (формат VC/Habr-типа платформ — экспертный лонгрид с конкретными данными/цифрами из исследования как фактурой).
2. **Пост** для соцсетей (короче, с хуком).
3. **Карусель** (слайд-структура: тезис на слайд).
4. **Сценарий короткого видео/ролика** (структура: хук → тело → призыв).

Ключевое требование к качеству: сгенерированный текст должен **использовать конкретную фактуру исследования** (реальные цифры Wordstat, конкретные evidence-цитаты с источниками из M1-M7, а не общие фразы) — то есть генерация должна показывать, что исследование было глубоким, а не выглядеть как generic-текст, который мог бы получиться и без него. Это и есть точка, где нужно обогнать конкурента.

Нужен ли отдельный «упаковочный» слой промптов поверх готовых результатов исследования (принимает JSON результатов M1-M7 → выдаёт текст в одном из 4 форматов), или переиспользовать часть инфраструктуры `buildSystem` (index.html:756)? Оценить на месте, в контексте текущей архитектуры.
- Один пайплайн с параметром формата (article/post/carousel/video-script), или разные функции на каждый формат? Учесть переиспользование фактуры (одна и та же исследовательская база должна уметь дать все 4 формата без повторного дорогого вызова исследования).

## Явно не входит в это ТЗ

- Монетизация, авторизация, биллинг — отдельный трек (Спринт 3 в `~/Projects/personal-brand/ROADMAP.md`).
- M9 (контент-радар) — остаётся отложенным по причинам из `ТЗ-АНАЛИТИЧЕСКИЙ-СЛОЙ.md`.
- Модульная платформа v2 (подключаемые модули под свои API-ключи клиента) — отдельная нерешённая гипотеза, не проектировать сейчас.

## Критерий готовности (v1 этого ТЗ)

Из одного законченного исследования (M1-M7 хотя бы одной ниши) можно сгенерировать минимум 2 из 4 форматов (например статья + пост), и владелица подтверждает на ручной экспертной проверке, что текст использует конкретную фактуру исследования, а не звучит generic.
